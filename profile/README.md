<p>买住宅 IP 资源时，多数人只问两个数：多少条、多少钱。真正上线才发现，同一批号散落在七八个国家，注册地写 A 国，出口落在 B 国，聊到一半地区还会自己漂。问题不在数量，在于「资源」这两个字被压成了一件事。它其实是三层叠在一起：线路从哪条家宽出来、归属登记在哪、调度怎么把号派进池子。下面按这三层拆开讲，顺带给出能照着做的核对单和判定阈值。</p>
<h2>一、把「资源」拆成线路、归属、调度三层</h2>
<p>三层不是并列的三个部门，而是从下往上的依赖关系。线路决定归属，归属决定你能不能按地区分组，调度决定同一批号会不会互相串。任何一层虚，上面两层都会跟着虚，所以排错也要从下往上走。</p>
<h3>线路层：出口到底是哪条家宽</h3>
<p>原生家宽的判断不靠服务商口头承诺，靠三条能查的证据。第一，ASN 要落在当地电信运营商名下，比如美国常见 Comcast、Verizon、AT&T，欧洲常见 Deutsche Telekom、Orange、Vodafone；机房段的 ASN 通常挂在 DigitalOcean、Vultr、Hetzner 这类托管商身上，一眼能分出来。第二，whois 的 netname 与 org-name 要和运营商对得上，用 whois -h whois.arin.net 或 RIPE 的查询入口即可。第三，反向解析常见形如 c-xx-xx-xx-xx.hsd1.ca.comcast.net，机房 IP 很少有这种命名习惯。</p>
<h3>归属层：注册地、时区、语言要能对上</h3>
<p>很多「看着不自然」不是 IP 的问题，是三个软信息错位：注册资料填的地区、浏览器时区、Accept-Language。IP 在洛杉矶，时区却固定 Asia/Shanghai，语言头只带 zh-CN，这种组合比机房 IP 更显眼。核对方法很土但有效：打开 chrome://version 看 UA 与实际启动参数，用 Intl.DateTimeFormat().resolvedOptions().timeZone 读浏览器时区，用 time.is 对系统时钟，NTP 偏差建议控制在一秒以内。三处都指向同一地区，再看 IP 才有意义。</p>
<h3>调度层：一批号怎么分进池子</h3>
<p>调度最容易随手做，也最容易埋雷。图省事的做法是「谁空闲给谁」，结果同一个号今天在东京、明天在法兰克福。稳妥的做法是按地区建池：一个国家一个池，必要时一个城市一个池，池内按线路 ID 编号；调度表里固定记录「号 → 池 → 线路」的对应关系，号不跨池迁移，池子没铺满时宁可留空，也不强行塞进去凑数。</p>

<h2>三、把「同一批」做成能复盘的记录</h2>
<img src="/tp.png" alt="住宅IP线路归属与ASN查询界面示意">
<p>批次是这套方法的最小管理单位。把同一批号、同一个地区池、同一段上线时间绑在一起，后面出问题才有对照物。台账不必复杂，一张表就够，但字段要固定，换人接手能直接看懂。</p>
<h3>批次台账的六个字段</h3>
<p>批次号（日期加池编号，例如 0326-US-LA）、创建日期、地区池名称、线路 ID 列表、环境指纹摘要（UA 主版本、时区、分辨率、字体数量）、当前负责人。指纹只存摘要不存全量，交接时不会把整份环境配置到处传，也方便比对是否被人动过。</p>
<h3>每周做一次抽样复核</h3>
<p>按百分之十抽样，抽到的号跑一遍 ipinfo 与 bgp 查询，比对 ASN 和城市是否还在原池。家宽线路的上游偶尔会被运营商调整，ASN 从 ISP 段漂到托管段就是硬信号，这条线要下线。复核结果写进「最近核对」列，超过两周未核对的标黄，标黄超过四条就排一次集中检查。</p>
<h2>四、该换池还是只换一条线</h2>
<p>判断标准建议写成阈值，别每次凭感觉。单条线路七天内连接失败三次以上，或者延迟中位数超过 800 毫秒并持续两天，只换这一条；整池里超过三成线路的 ASN 变成托管段，或者城市级定位连续一周飘到别的城市，整池下线重建。阈值不必照抄，按自己业务的容忍度定，但要落在纸面上，否则每次讨论都要重新争一遍。</p>
<h3>迁号时的先后顺序</h3>
<p>先在新池把环境铺好，跑通登录和一两次常规对话，再迁号。不要先停旧线再找新线，中间空窗最容易出岔子。迁完保留旧线三到七天当回滚通道，确认新线稳定再回收，账号侧的登录记录也不会出现突兀的断档。</p>
<h2>常见问答</h2>
<h3>同一批号一定要落在同一个城市吗？</h3>
<p>答：不强制，但同一批号落在同一城市最省心。城市级一致能让时区、语言、邮编这些软信息一次对齐；如果业务需要跨城市，至少做到同一批同一个国家，并且每批的调度表里写清城市，不要出现同号跳城的情况。</p>
<h3>注册资料填国内地区、出口在国外，会有问题吗？</h3>
<p>答：两套信息打架时，任何平台都可能要求额外确认。稳妥的做法是让资料地区、账单地区、出口地区尽量同源；确实需要跨地区，也把时区和语言调到与出口一致，减少可被注意到的矛盾点，而不是靠反复更换出口去碰运气。</p>
<h3>家宽线路的 ASN 会变吗？</h3>
<p>答：会。运营商调整上游、线路被转售、服务商更换供应商，都可能让 ASN 变化。判断方法很简单：把每次核对的 ASN 记在台账里，一旦从 ISP 段变成托管段，就说明这条线已经不是原来那条，应该按换线处理。</p>
<h3>一个地区池放多少条线路比较合适？</h3>
<p>答：按号的在线密度倒推，常见做法是一个池子留百分之十五到二十的余量。池子太满，任何一条线出问题都没有替换位；池子太空，单条成本又被摊高。先用小量试跑一周，看峰值并发，再决定扩到多少条。</p>
